## Findings

### [stage-1 + stage-2, merged] Runtime renders/validates the live draft schema, not the published snapshot

- **Cite:** `server/api/src/app/schemas/schemas.service.ts:119-131`
- **AC:** AC-14 (also affects AC-15/AC-16 content and AC-18 validation, since `get`/`submit` in `forms-data.controller.ts:36,50` both read from this method)
- **Problem:** `findPublishedById` gates existence on `schemasVersions.length > 0` but returns `schemas.schema` (the live, mutable draft) instead of the pinned `schemasVersions` snapshot. A Creator who publishes then keeps editing (or breaks) the draft has those unpublished edits served to Users in Runtime immediately, with no republish step — the reachable content is not the _published_ content.
- **Independently corroborated** by both the stage-1 (AC-trace) and stage-2 (quality) reviewers from different angles.
- **Verdict:** CONFIRMED
- **Resolution:** Fix now → follow-up task for `implement`.

### [stage-1] AC-16 fallback covers resolve-time failures only, not render-time uncaught errors

- **Cite:** `client/apps/runtime/src/app/form-viewer/form-viewer.ts:210-251` (resolveField try/catch), `form-viewer.html:39-43`
- **AC:** AC-16
- **Problem:** AC-16 defines a rendering failure as "raises an uncaught error **or** cannot resolve its bound data." The try/catch only wraps config _resolution_ (missing/unrecognized `x-ui`); there is no `ErrorHandler`/render-boundary, so a component that throws during actual rendering/change-detection still blanks the whole view — the exact outcome AC-16 forbids.
- **Verdict:** CONFIRMED
- **Resolution:** Fix now → follow-up task for `implement`.

### [stage-2] Submitted `values` accepts arbitrary unknown keys with no size bound

- **Cite:** `server/api/src/app/forms-data/forms-data.validation.ts:17-46`, `server/api/src/app/forms-data/dto/submit-forms-data.dto.ts:9-10`
- **Problem:** the DTO only asserts `@IsObject()`; `validateFormValues` only inspects keys declared in the schema, so extra/unknown keys pass straight through into the `jsonb` column unbounded — contradicts data-model.md's "keyed like the schema's component ids" contract.
- **Verdict:** CONFIRMED
- **Resolution:** Fix now → follow-up task for `implement` (strip `values` to the schema's known field ids before upsert).

### [stage-2, low priority, no AC] `textColor` is parsed but never applied on render

- **Cite:** `client/apps/runtime/src/app/form-viewer/form-viewer.ts:237,271`, `form-viewer.html:13-37`
- **Problem:** a Creator-set text colour is silently dropped in Runtime — cosmetic rendering-fidelity gap, not tied to any AC.
- **Verdict:** CONFIRMED
- **Resolution:** Fix now → follow-up task for `implement` (bind `[style.color]` on the item wrapper).

### [stage-2, non-blocking] Some unit tests assert `where: expect.anything()` instead of the real scoping predicate

- **Cite:** `server/api/src/app/forms-data/forms-data.service.spec.ts:36-38,90-97`
- **Problem:** the `getOwn`/`deleteOwn` unit tests can't by themselves prove the query is scoped to `schemaId AND userId`. Compensated by the real-DB `forms-data.isolation.spec.ts`, which genuinely proves AC-20 cross-account isolation.
- **Verdict:** PLAUSIBLE (real gap in unit-level signal, but functional property is proven elsewhere)
- **Resolution:** Not an issue — accepted as-is; the security property is proven by the isolation spec.
